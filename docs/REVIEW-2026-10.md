## 1. Sicurezza

### 🔴 S1 [CONFERMATO] Keystore Android + password hardcoded nel repo
`evershelf-kiosk/evershelf.jks` e `evershelf-health-bridge/evershelf.jks` sono
**committati**, e la password è **in chiaro** nel build script:
```
evershelf-kiosk/app/build.gradle.kts:21-24
  storeFile = file("../evershelf.jks")
  storePassword = "evershelf123"
  keyAlias = "evershelf"
  keyPassword = "evershelf123"
```
(idem `evershelf-health-bridge/app/build.gradle.kts:20-23`).
**Impatto**: chiunque ha la chiave di firma dell'app → può pubblicare APK
"aggiornamento" che Android accetta come autentici e impersonare l'app.
**Fix**:
1. NON riscrivere la storia se il keystore è già distribuito (invaliderebbe gli
   update installati): al minimo **ruotare** la chiave e cambiare password.
2. `git rm --cached` dei `.jks`, aggiungere `*.jks` a `.gitignore`.
3. Passare ai **Gradle secrets** (`storeFile`/`storePassword` da env o
   `keystore.properties` non versionato / GitHub Secrets nel workflow `build-kiosk.yml`).
4. Se si vuole ripulire la storia: `git filter-repo` + force-push (con backup).

### 🟠 S2 [CONFERMATO] SSRF nell'endpoint `tts_proxy`
`api/index.php:2247` — l'URL è **fornito dal client** e passato a `curl_init($url)`
senza allowlist di host. Sono iniettati solo i token server per `HA_URL`/`TTS_URL`,
ma la richiesta parte comunque verso **qualsiasi** URL. Con `CURLOPT_SSL_VERIFYPEER
= false` (riga ~2296) e col default **`API_TOKEN` vuoto** (nessuna auth), un
attaccante sulla LAN può usare il server per:
- raggiungere servizi interni (`http://127.0.0.1:<porta>`, `http://10.x/…`),
- leggere metadata cloud (`http://169.254.169.254/…`),
- esfiltrare il corpo della risposta (viene rimandato al chiamante, riga ~2306).
**Fix**: allowlist di host (riusare `evershelfScaleHostAllowed()`), rifiutare IP
privati/link-local, richiedere sempre autenticazione per `tts_proxy`, non
disabilitare `SSL_VERIFYPEER` (o renderlo opt-in esplicito, non default).

### 🟠 S3 [CONFERMATO] Iniezione / distruzione di `.env` in `save_settings`
`api/index.php:8240-8265` scrive il file concatenando valori non sanificati:
```php
foreach ($envVars as $key => $val) { $lines[] = "{$key}={$val}"; }
```
Un valore che contiene `\n` (es. incollato o via API) **inietta chiavi arbitrarie**
nel `.env` (es. `---\nHA_TOKEN=...`). Inoltre la riscrittura **cancella tutti i
commenti e l'ordine** di `.env.example`. Stesso problema in
`_gdriveSetEnvVar()` (`api/index.php:12810-12817`).
**Fix**: `strip` di `\r\n` sui valori, quoting/escaping dei valori con spazi o
caratteri speciali, e riscrittura **chirurgica** (sostituire solo la riga `KEY=`).

### 🟠 S4 [CONFERMATO] XSS memorizzato nella vista Log
`assets/js/app.js:18338` e `:18344` interpolano **senza escape** dati controllabili
dall'utente, poi inseriti via `innerHTML`:
```js
const brand = tx.brand ? ` <em>(${tx.brand})</em>` : '';   // 18338 — NON escapato
const notes = tx.notes && ... ? ` · ${tx.notes}` : '';      // 18344 — NON escapato
...
html += `<div class="log-product"><strong>${escapeHtml(tx.name)}</strong>${brand}...`
html += `<div class="log-detail">...${notes}...</div>`       // 18355/18359
```
`brand` e `notes` arrivano da prodotti/transazioni (editabili e importabili). Un
`brand` = `<img src=x onerror=alert(document.cookie)>` viene eseguito.
**Aggravante**: `escapeHtml()` (`assets/js/core/dom.js`) usa `textContent→innerHTML`
quindi escapa solo `& < >` e **non** `"` né `'` → non è sicuro nei contesti
**attributo** e **JS inline** (vedi B1). **Fix**: usare `escapeHtml` su `brand`/`notes`;
introdurre un `escapeAttr()` che gestisca anche le virgolette, o (meglio) costruire
i nodi con `textContent`/`document.createElement`.

### 🔵 S5 [CONFERMATO] Superficie esposta di default (nessun `API_TOKEN`)
Se `API_TOKEN` è vuoto (default di installazione), sono aperti senza
autenticazione: `report_error`, `report_bug`, `client_log` (scrivono su disco →
*log/disk flooding*), `check_update`, oltre a `get_logs` (che richiede il token
**solo se configurato**). In un deployment esposto su Internet è una superficie
da chiudere. **Fix**: non rendere `API_TOKEN` opzionale, oppure limitare
`get_logs` alle sole richieste locali e rate-limitare gli endpoint di report.

### 🔵 S6 [CONFERMATO] `CURLOPT_SSL_VERIFYPEER = false` su `tts_proxy`
`api/index.php` (~2296): disabilita la verifica TLS "per cert self-signed".
Accettabile in LAN, ma combinato con S2 è rischioso. **Fix**: default `true`,
override esplicito per-host fidato.

### 🔵 S7 [CONFERMATO] CORS condizionale
`evershelfSendCorsHeaders()` invia `Access-Control-Allow-Origin` solo se
`CORS_ORIGIN` è impostato: bene. Verificare però che l'origine venga **riflessa
solo se esattamente uguale** (no `*` con credenziali). [DA VERIFICARE] con
`CORS_ORIGIN` configurato.

## 2. Bug funzionali / comportamentali

### 🟠 B1 [CONFERMATO] `escapeHtml()` non escapa `'` e `"` → rottura attributi / JS inline
`assets/js/core/dom.js` implementa l'escape via `textContent`, che NON tocca le
virgolette. Dove il risultato finisce dentro un attributo o una stringa JS inline
si rompe l'HTML/JS. Esempi reali:
- `app.js:2646` → `title="${escapeHtml(r.name)}"`: un prodotto con `"` chiude
  l'attributo → iniezione di attributi (vettore XSS).
- `app.js:18363` → `onclick="undoTransactionEntry(${tx.id}, '${escapeHtml(tx.type)}',
  '${escapeHtml(tx.name || '')}')"`: un apostrofo nel nome rompe la stringa JS.
- `app.js:3548-3549` → `onclick="_backupRestore('${b.filename}')"` /
  `_backupDelete('${b.filename}')`: `b.filename` **non escapato** (proviene dal
  server, quindi a rischio più basso, ma resta un pattern fragile).
**Fix**: `escapeAttr()` che sostituisca anche `" '` (e `` ` `` per i template), e
preferire `addEventListener` + `dataset` al posto degli `onclick` inline.

### 🟡 B2 [CONFERMATO] La riscrittura di `.env` perde commenti e ordine
Conseguenza di S3: dopo **un qualsiasi** salvataggio impostazioni, `.env` viene
ricostruito solo da `KEY=valore` (righe 8241-8244) → tutti i commenti di
`.env.example` spariscono e il file diventa illeggibile/diffuso male. Molti
utenti copiano `.env.example` in `.env` proprio per i commenti. **Fix**: update
in-place riga per riga (preservare commenti e righe non modificate).

### 🟡 B3 [CONFERMATO] File JSON di runtime tracciati in git
Sono versionati file che l'app **riscrive a runtime**:
`data/ai_usage.json`, `data/anomaly_dismissed.json`, `data/backup_last_ts.json`,
`data/shopping_name_cache.json`, `data/shopping_total_cache.json`.
**Impatto**: churn continuo, conflitti di merge, possibile commit di dati
personali (spesa/consumi) e divergenza tra ambienti. **Fix**:
`git rm --cached data/ai_usage.json data/anomaly_dismissed.json data/backup_last_ts.json
data/shopping_total_cache.json` e aggiungerli a `.gitignore`; mantenere solo i
dataset **statici** (`seasonal_produce_it.json`, `shopping_name_cache.json` se è
davvero curato a mano). Nota: dopo `git rm --cached` i deploy esistenti vanno
inizializzati con un file vuoto (`{}`/`[]`) al primo avvio.

### 🟡 B4 [DA VERIFICARE] Parsing delle date assunto in UTC
`app.js:18315` (`new Date(tx.created_at + 'Z')`) e vari altri punti forzano la
`Z` (UTC) sulle date provenienti dal DB. Se il server SQLite scrive
`datetime('now')` (UTC) va bene — ma alcune tabelle/colonne potrebbero usare
`CURRENT_TIMESTAMP` con impostazioni diverse, o timestamp "locali" da Bring/HA.
**[DA VERIFICARE]**: confrontare in modo sistematico se **tutti** i timestamp
salvati sono UTC. In caso contrario si hanno spostamenti di fuso nelle viste
log/statistiche. **Fix**: standardizzare su UTC e documentarlo, oppure far
serializzare al backend ISO-8601 con offset.

### 🔵 B5 [CONFERMATO] `get_logs`: filtro di livello correttamente validato (nessun bug)
`api/index.php:172-175`: il filtro livello è validato con `in_array`. OK. Nessun
bug, citato solo per chiarezza (è tra i pochi endpoint che fanno bene).

### 🔵 B6 [CONFERMATO] Early-exit fuori dal rate-limit
Gli action DB-free (`ping`, `get_logs`, `gemini_usage`, `health_check`) sono
gestiti **prima** di `checkRateLimit()` (riga 709/786) → non rate-limitati.
Per `get_logs` c'è il controllo token (solo se configurato) ma `ping`/`gemini_usage`
sono liberi. Impatto basso ma è una superficie di abuso (polling). **Fix**:
applicare il rate-limit anche a questi o limitarli al loopback.

## 3. Problemi latenti / rischio tecnico

### 🟡 L1 Monoliti difficili da mantenere
`api/index.php` ~19.5k righe / 410 funzioni e `assets/js/app.js` ~25.6k righe /
913 funzioni globali. `docs/ARCHITECTURE.md` già prevede uno split
(`api/handlers/*`, `assets/js/features/*`). Ogni modifica rischia regressioni
"a distanza"; i tool di analisi fanno fatica. → cfr. §4 Pulizia (P1/P2).

### 🟡 L2 913 funzioni JS nello scope globale
Nessun modulo/namespace → rischi di collisioni e `this`/state impliciti. Il file
ha già `assets/js/core/*` davanti: conviene estendere quel pattern.

### 🟡 L3 Stato globale mutabile + coda offline
La logica di retry/offline queue dentro `api()` dipende da variabili globali non
incapsulate e non testate automaticamente → difficile da reggere in caso di
richieste concorrenti. Aggiungere test (vedi L5).

### 🔵 L4 Nessun test automatico visibile
La CI fa lint/build/i18n ma **non** esegue test funzionali. Anche solo un paio di
test su `smartShopping`, guardie quantità e `seasonal` ridurrebbero molto i
regressi. Vedi §5 (idea test harness). [DA VERIFICARE] l'assenza reale di una
dir `tests/`.

### 🔵 L5 Endpoint pubblici che scrivono su disco
`report_error`/`client_log` (pubblici) scrivono log → possibile riempimento disco
se non rate-limitati/puliti. Verificare il cron di rotazione e un limite di
dimensione. [DA VERIFICARE]

## 4. Ottimizzazioni (performance)

### 🟡 O1 Query "hot" e indici
Buona base: esistono già indici compositi mirati
(`idx_transactions_type_date`, `idx_transactions_pid_type_undone`). Verificare
con `EXPLAIN QUERY PLAN` le query di:
- `inventory_list` (filtro per `location` + join products) → assicurare uso di
  `idx_inventory_location` e, se presente la ricerca testuale, introdurre un
  indice su `products(name)` (o FTS5).
- `smartShopping` / predizioni consumi (aggregano su tutto lo storico) →
  valutare una **vista materializzata** o una tabella di riepilogo aggiornata
  via cron (evita full-scan ad ogni richiesta).
- `transactions_list` con paginazione (`LIMIT/OFFSET`) → `OFFSET` alto è lento;
  valutare keyset pagination (`WHERE id < :last`).
[DA VERIFICARE] con dati reali e `EXPLAIN QUERY PLAN`.

### 🟡 O2 Caching eccessivo / mancante
Molti risultati AI sono già in cache JSON (`smart_shopping_cache.json`,
`category_ai_cache.json`, …). Verificare che ogni cache abbia **TTL/invalidazione**
(budget di token e dati stantii). Le cache JSON non sono transazionali:
letture/scritture concorrenti possono corrompere il file → usare scrittura atomica
(`file_put_contents` su file temporaneo + `rename`).

### 🔵 O3 Polling e payload
Il client fa poll frequenti (`stats`/`smart_shopping`/heartbeat). Applicare
`ETag`/`If-None-Match` o un timestamp `updated_at` per rispondere `304` e ridurre
bandwidth/batteria (importante sul kiosk). [DA VERIFICARE] la frequenza dei poll.

### 🔵 O4 Compressione e asset
Servire i JSON con `gzip`/`brotli` (Apache `mod_deflate`) e `Cache-Control`
corretto per `assets/vendor/*` (Tesseract/transformers). Ridurre il peso
iniziale: `app.js` 1.2 MB non minificato.

### 🔵 O5 Bootstrap backend
`api/bootstrap.php` carica **tutte** le lib ad ogni richiesta, anche per action
semplici. Per azioni frequenti si può caricare lazy solo ciò che serve → riduzione
latenza.

## 5. Pulizia / refactoring

### 🟡 P1 Spezzare `api/index.php`
Estrarre i gruppi di handler in `api/handlers/*.php` (products, inventory, ai,
shopping, settings, integrations) come già pianificato in
`docs/ARCHITECTURE.md`. Il `switch` resta come router; `bootstrap.php` carica solo
i gruppi necessari. Riduce drasticamente il costo di lettura/modifica.

### 🟡 P2 Spezzare `assets/js/app.js`
Dividere in `assets/js/features/*.js` (scan, add, inventory, shopping, settings,
tts) con un piccolo event-bus. Già esistono `core/dom.js` e `core/auth.js`:
estendere quel pattern. Vantaggio: cache-busting e caricamento per-pagina.

### 🔵 P3 Uniformare la sicurezza `.env`/log
Centralizzare scrittura `.env` (S3/B2) e logging (`EverLog`) in un unico modulo,
con escaping e test.

### 🔵 P4 De-duplicazione media
`assets/img/demo.gif` (9.8 MB) e `assets/EverShelf.gif` (9.8 MB) sono due copie
quasi identiche; i file Tesseract `*-core.wasm.js` (4.6 MB × 2) duplicano la
variante SIMD/non-SIMD. Valutare se il non-SIMD è ancora necessario. Spostare i
gif README su CDN/release assets.

### 🔵 P5 `.bak`/scratch già esclusi (positivo)
L'aggiunta in `.gitignore` di `*.bak*`, `*.orig`, `*.rej` e degli scratch è
corretta. Resta il `git rm --cached` per gli APK pesanti (L6) e per i JSON
runtime (B3).

### 🔵 P6 Uniformare le versioni
La versione va bumpata in 4 punti (`index.html` ×2, `manifest.json`, `sw.js`).
Facile dimenticarne uno → introdurre `version.json` letto a build-time o uno
script `scripts/bump-version.sh`.

## 6. Igiene del repository (bloat & supply chain)

### 🟡 L6 [CONFERMATO] Binari pesanti e duplicati tracciati
- APK: `evershelf-kiosk.apk` (6.7 MB), `evershelf-kiosk-latest.apk` (5.6 MB),
  `releases/evershelf-kiosk.apk` (6.7 MB) → **~19 MB** e duplicati.
- Media: `assets/img/demo.gif` + `assets/EverShelf.gif` ~19.6 MB.
**Fix**: gli APK appartengono alle **GitHub Releases** (già usate da
`build-kiosk.yml`), non al tree. `git rm --cached` + `.gitignore`.

### 🔵 L7 File locali non tracciati
`ca.crt`, `data/dispensa-ca.crt`, `TODO.md` esistono nel working tree e non sono
versionati (bene). `ca.crt` sembra una CA locale per TLS self-signed: assicurarsi
che **non** venga committata per errore.

### 🟡 L8 [CONFERMATO] Dipendenze con vulnerabilità note (Dependabot)
Al momento del push, GitHub segnala **12 vulnerabilità** sul branch di default
(5 high, 7 moderate) — visibili in
`https://github.com/dadaloop82/EverShelf/security/dependabot`. Riguardano
verosimilmente le dipendenze JS (`mcp-server/`, eventuali dev deps) e/o Gradle
Android. **Fix**: `npm audit fix` / bump delle dipendenze; per Android
aggiornare Gradle/AGP e le librerie. Non riguarda il codice PHP/JS
dell'applicazione ma va chiuso (supply chain). [DA VERIFICARE] quali pacchetti.

## 7. Idee e nuove feature

> Coerenti con l'architettura esistente (PHP+SQLite+vanilla JS, i18n, cron).

- 💡 **F1 Test harness minimale**: `tests/` senza dipendenze pesanti (o `pest`),
  più `npm test` con jsdom per funzioni pure (`smartShopping`, guardie quantità,
  `formatQuantity`). Girabile in CI.
- 💡 **F2 Autenticazione reale opzionale**: PIN/login per-utente + wizard che
  obbliga `API_TOKEN` al primo avvio. Oggi è "aperto salvo configurazione".
- 💡 **F3 FTS5 per la ricerca prodotti**: indice full-text su
  `products(name, brand, notes)` → ricerca istantanea su migliaia di righe.
- 💡 **F4 Report spreco con grafici**: esistono `waste` e `monthly_stats`;
  aggiungere un report mensile/anno con % spreco vs consumato ed export CSV/PDF.
- 💡 **F5 Sincronizzazione multi-istanza**: merge opzionale via export/import
  incrementale (delta) o sync P2P LAN per utenti con più case/dispositivi.
- 💡 **F6 Ricette → lista spesa in un tap** con scorporo automatico delle
  giacenze (parte già presente: `chat_to_recipe`/`recipe_from_ingredient`);
  manca il confronto automatico con l'inventario e l'aggiunta selettiva.
- 💡 **F7 Notifiche push/webhook scadenze** riusando `_fireHaWebhook()` verso
  endpoint generici (ntfy/Telegram/Apprise), oltre a Home Assistant.
- 💡 **F8 Modalità "casa vacanza/ospiti"**: profili inventario separati
  (tag su `location` o `household_id`) per non sporcare le statistiche.
- 💡 **F9 Backup automatico cifrato**: i backup locali/GDrive sono in chiaro →
  cifratura at-rest con password utente.
- 💡 **F10 Accessibilità**: audit con axe, contrasto e `aria-*` sistematica
  (buona base già presente con `data-i18n-aria`).
- 💡 **F11 Suggerimenti "zero waste" contestuali**: usa `seasonal.php` +
  `opened_shelf_life` + `consumption_predictions` per proporre ricette che
  consumano ciò che sta per scadere (chiude il ciclo anti-spreco).
- 💡 **F12 PWA offline-first completa**: today c'è la offline queue; rendere
  consultabili inventario e lista spesa completamente offline.

## 9. Cosa è fatto bene (da NON toccare)

- SQL parametrizzato quasi ovunque; le due interpolazioni (`LIMIT {$limit}`,
  `id = {$id}`) operano su valori `intval()`-cast → non sfruttabili.
- Validazione rigorosa dei nomi file di backup via regex
  (`deleteLocalBackup`/`restoreLocalBackup`, righe 12767/12782) → **nessun path
  traversal**.
- `tts_proxy` scarta gli header di auth forniti dal client (buono), anche se
  resta SSRF (S2).
- `.htaccess` che nega `data/`, `logs/` e `.env`; nessun `.env`/`.bak` tracciato.
- Indici compositi già presenti sulle query più calde.
- Logging centralizzato con livelli e rotazione (`EverLog`).
